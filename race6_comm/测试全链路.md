### 0.1 ★ 为什么软件编号必须从 0 开始（不能直接用 1~6）

`ego_replan_fsm.cpp:173` 的起跑条件是

```cpp
drone_id <= 0 || (drone_id >= 1 && have_recv_pre_agent_)
```

而 `have_recv_pre_agent_` 只有在收到 **`drone_id = 0` 的轨迹**之后才置真
（`:1306-1320` 的循环从 `i = 0` 开始，要求 `swarm_traj[0].drone_id == 0`）。
⇒ 六台若都用 1~6，没有一台的 id 是 0，**六台全都不起飞**，FSM 会一直打印：

```
[FSM]: state: SEQUENTIAL_START, Drone:N. Waiting for prev traj,
```

看到这行一直刷 = **编号问题或通讯没通**（两个都查）。

### 0.2 四条通道（Multibotnet 只搬这四样）

| 通道 | 本机发布 | 本机接收 | 消息类型 | 端口 | 作用 |
|---|---|---|---|---|---|
| 轨迹规划 | `/broadcast_traj_from_planner` | `/broadcast_traj_to_planner` | `controller_msgs/MinTraj` | 4001 | **协同避碰的唯一依据** |
| 里程计 | `/mavros/local_position/odom` | `/mbn/droneN_odom` | `nav_msgs/Odometry` | 4101 | 监控用（**不参与避碰**，要 mavros 在跑才有数据） |
| 时间同步 | `/race6/timesync_tx` | `/race6/timesync_rx` | `std_msgs/Float64MultiArray` | 4201 | 测两机时钟差 |
| 链路测试 | `/race6/comm_test_tx` | `/race6/comm_test_rx` | `std_msgs/Float64MultiArray` | 4401 | 丢包/延迟/内容校验 |

**铁律：每条通道的发和收必须是两个不同的名字**，否则 Multibotnet 会把收到的再广播出去 → 广播风暴。

### 0.3 为什么 PC 上要生成 `six_ws`，而飞机上**不要**

先搞清楚 `six_ws` 到底是什么：**它就是一个空的 catkin 工作区外壳**，里面没有自己的源码，
只有指向仓库的软链：

```
~/six_ws/                                          ← 生成物，随时可删可重建，不入 git
├── src/
│   ├── CMakeLists.txt        ← catkin_init_workspace 生成的 toplevel 入口
│   ├── race6_comm     -> ~/SixBotsRace/race6_comm                （软链）
│   ├── multibotnet    -> ~/SixBotsRace/third_party/multibotnet   （软链）
│   └── third_party/controller_msgs -> …                          （软链）
├── build/                    ← catkin_make 产物
└── devel/setup.bash          ← 你要 source 的就是这个
```

**为什么必须有"一个"工作区**：ROS 1 里一个包要被 `rosrun`/`roslaunch`/`rospack` 看见，
它的**上级目录必须在 `ROS_PACKAGE_PATH` 上**；而把包放上去（并编译 C++ 部分）的标准手段就是
catkin 工作区。`~/SixBotsRace` 是**源码仓库**（顶层是 `race6_comm/`、`third_party/`，没有 `src/`），
`catkin_make` 不能在它上面跑，ROS 也就看不见里面的包 —— 这就是"`rospack find race6_comm` 找不到"的根因。

**那为什么 PC 上要新建、飞机上不新建？**

| | PC | 飞机 |
|---|---|---|
| 已有工作区？ | 没有（或被清掉了） | **有**：`~/chen_ws`，已编好、已 source、带着 Sophus/PCL/mavros/livox |
| 做法 | 生成 `~/six_ws`（最小、专用） | **把两个新包塞进 `~/chen_ws/src/`**，不要另建 |
| 命令 | `bash …/setup_six_ws.sh --minimal` | `WS=$HOME/chen_ws bash …/setup_six_ws.sh --minimal --no-lab` |

**PC 上为什么值得专门建一个小的**（而不是塞进某个大工作区）：
`catkin_make` 会编译工作区里的**所有**包。放进大工作区 = 每次都要编整个实验室栈（慢），
而且**任何一个无关的实验室包编不过，你就连通讯都没法测**。`six_ws` 只含 3 个包，30 秒编完，
与实验室代码的编译状态完全解耦。

**飞机上为什么绝不能另建**：
① 机载电脑上重编一整套实验室代码要装 Sophus/PCL/livox，还可能根本没外网；
② 更致命的是会**同时存在两个被 source 的工作区** —— 谁的 `setup.bash` 后 source，
谁的 `ROS_PACKAGE_PATH` 就盖住前者，于是出现"**上次能 launch、这次找不到包**"这种最难查的现象。
（你们已经踩过一次了。）

**所以规则是一句话：一台机器上只保留一个被 source 的工作区。**

| 机器 | 工作区 | 怎么来的 |
|---|---|---|
| PC | `~/six_ws` | `setup_six_ws.sh` 生成（软链指向仓库） |
| 飞机 | `~/chen_ws` | 飞机原有的；只往里加 `race6_comm` + `multibotnet` 两个软链 |

两边都靠**软链**指向同一个 git 仓库 ⇒ **仓库是唯一真源**，`six_ws` 随便删，不会有代码丢失。

> 脚本名叫 `setup_six_ws.sh` 是历史遗留（它其实干的是"把包放进某个工作区"）。
> 它靠环境变量 `WS` 指定目标工作区，**默认值只是给 PC 用的便利**：
>
> - 不传 `WS` → 生成 `~/six_ws`（PC）
> - `WS=$HOME/chen_ws` + `--no-lab` → 复用飞机已有工作区，且绝不碰里面的实验室包

## 2. 阶段二：配置时间同步

**为什么必须做**：`ego_replan_fsm.cpp:1222-1237` 用「本机时钟 − 消息里的发送方时钟」判定，
`> 0.25 s` 刷告警、`> 10 s` **直接丢弃轨迹**。两机时钟差就等于这个差值。

### 2.1 源机：**物理 1 号机**（192.168.66.101）

```bash
sudo apt install -y chrony
sudo systemctl disable --now systemd-timesyncd 2>/dev/null || true   # 别让两个 NTP 客户端打架
sudo cp /etc/chrony/chrony.conf /etc/chrony/chrony.conf.bak
sudo tee /etc/chrony/chrony.conf >/dev/null <<'EOF'
driftfile /var/lib/chrony/chrony.drift
allow 192.168.66.0/24
local stratum 8
makestep 0.1 3
rtcsync
EOF
sudo systemctl restart chrony
sudo systemctl enable  chrony       # ★ 开机自启（不设这行，换电池/重启后不会自动对时）
```

### 2.2 其余各台（客户端，把 IP 换成源机 IP）

```bash
sudo apt install -y chrony
sudo systemctl disable --now systemd-timesyncd 2>/dev/null || true
sudo cp /etc/chrony/chrony.conf /etc/chrony/chrony.conf.bak
sudo tee /etc/chrony/chrony.conf >/dev/null <<'EOF'
driftfile /var/lib/chrony/chrony.drift
server 192.168.66.101 iburst
makestep 0.1 3
rtcsync
EOF
sudo systemctl restart chrony
sudo systemctl enable  chrony       # ★ 同上
```

> **不需要互联网**：`local stratum 8` 让源机在没有外网时用自己的钟当权威源。
> 代价是"绝对时间可能不准，但六台一致" —— 这对 FSM 判据完全够用，只是 bag 时间戳会不对。
> 想让绝对时间也准，在**源机**里加一行 `pool ntp.aliyun.com iburst`（有外网就用，没有自动退回）。

### 2.3 开机自动同步的三个条件（每台查一遍）

```bash
systemctl is-enabled chrony             # 期望 enabled
systemctl is-active  chrony             # 期望 active
systemctl is-enabled systemd-timesyncd  # 期望 disabled 或 masked
```

**条件③：源机（物理 1 号机）要在网。** 它没上电时其余各台会一直重试（chrony 不会放弃），
源机一出现就自动连上；在那之前只能靠 driftfile 和本机晶振走，会慢慢漂开。

### 2.4 验证（三重证据，逐级变严）

```bash
# 证据1：操作系统层
chronyc sources -v        # 客户端：源机那行前面应是 ^*，Reach 攒到 377
chronyc tracking          # ★ 客户端上 System time ≈ 两机时钟差，期望毫秒级

# 证据2：Multibotnet 真实报文路径上（脚本，两台都要起通信，见阶段三）
rosrun race6_comm race6_time_sync.py --self-id <本机软件编号> --peers <对端软件编号>
#   看 |offset| 峰值 < 50 ms

# 证据3：直接上 FSM 的判据 → 见阶段三的 MinTraj 测试里那一列 dt
```

> ⚠️ **必须在客户端上读 `chronyc tracking`** —— 源机是跟自己比，`System time` 永远 ~0。
> ⚠️ **飞行中绝对不要** `chronyc makestep` 或 `race6_time_sync.py --apply`：步进时钟会毁掉正在执行的轨迹。

## 3. 阶段三：配置并验证 Multibotnet 通讯

### 3.1 检查配置里的 IP（**最容易出错的一步**）

配置里现在是 `192.168.66.101..106` 的**占位值**。把它改成六台的**真实 IP**：

```bash
# 先在每台飞机上查真实 IP
ip -4 addr show | grep -w inet

# PC 上：一条命令重生成全部配置（顺序 = 物理 1~6 号机）
cd ~/SixBotsRace/race6_comm
python3 scripts/gen_race6_configs.py --ips <物理1IP>,<物理2IP>,<物理3IP>,<物理4IP>,<物理5IP>,<物理6IP>
#   它会同时写 config/race6/drone_0..5.yaml 和 config/ground2/drone_0,1.yaml，
#   两者永远一致，不会"改了一处忘了另一处"

# 自检（含跨文件一致性）
python3 scripts/check_config.py --all        # 必须全绿

cd ~/SixBotsRace && git add race6_comm && \
  git commit -m "config: 填入六机真实 IP" && git push
```

> ⚠️ **强烈建议把 IP 固定下来**（网卡静态 IP，或在移动信号站上做 DHCP 保留）。
> 默认 DHCP 会在换电池/重启后重新分配，配置当场失效 —— 这是现场最难查的一类问题。
> 测哪两台，就至少保证那两台的 IP 填对了；其余四台保持占位 IP 也无害（是合法 IP 字面量，不会触发 DNS）。

### 3.2 起通信（每台一个终端）

```bash
source ~/chen_ws/devel/setup.bash

# ★ 对测两台（例如物理 3 号机 + 物理 5 号机）—— 强烈建议先做这一步
#   物理 3 号机：
bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh 3 --pair=5
#   物理 5 号机：
bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh 5 --pair=3

# 六台全上时，每台只报自己的物理编号（--pair 不要加）：
bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh 3
```

> **★ 正式比赛前的双机 / 三机测试**：起通信的方式要和比赛**完全一样**（不发假轨迹），
> 只额外留一个只读的 `race6_time_sync` 当连通性体温计 —— 加 `--race` 即可（细节见
> `比赛日启动清单.md` §④b-1）：
> ```bash
> bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh 3 --race --pair=5   # 双机
> bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh 3 --race --peers=0,1  # 三机
> ```

`race6_launch.sh` 会自动做四件事：
① 物理编号 → `drone_id`（= 物理编号 − 1）
② 算好 `peers`（`--pair=5` → 只期望 drone4；不带 `--pair` → 期望其余 5 台）
③ 选对 `config/race6/drone_<id>.yaml`
④ **拿本机真实 IP 和配置里 `drone<id>` 那一行比对，不一致就拒绝启动**（专治"配置拷错机器"）

先干跑一次看它要干什么：`bash race6_launch.sh 3 --pair=5 --dry-run`

> ⚠️ **两台对测必须加 `--pair=`**。不加的话脚本会期望另外 5 台都在，
> 没开机的 4 台会被判成"完全没有收到" → 明明通了却报 FAIL。
>
> 里程计那一路要有数据，得另开一个终端起 mavros（**不要加 `&`**，否则 Ctrl+C 停不掉）：
> `roslaunch mavros px4.launch`

### 3.3 看配置表（前 3 秒，一条判读口诀）

Multibotnet 启动后会打印配置表。**只看 Receive Topics 那几行**：

```
Receive Topics (4):
  /broadcast_traj_to_planner <- 192.168.66.105:4001     ← 必须是 IP！
  /mbn/drone4_odom           <- 192.168.66.105:4101
  /race6/timesync_rx         <- 192.168.66.105:4201
  /race6/comm_test_rx        <- 192.168.66.105:4401
```

> **口诀：`<-` 后面必须是 IP。显示成一个"名字"（例如 `<- drone0:4001`）就说明
> 这个别名没在配置的 `IP:` 段里定义** —— Multibotnet 会把名字当主机名去解析，
> 解析不了就永远连不上，**而且一个错都不报**（只在"接收计数一直是 0"上体现）。
> 想收到的对端没出现、或者出现的是别的 IP，都说明配置/节奏不对。

同时应看到若干条（每条通道首次收到数据时打印一次）：

```
[INFO] Topic '/broadcast_traj_to_planner' [controller_msgs/MinTraj] receiving data from network
[INFO] Topic '/race6/timesync_rx' [...] receiving data from network
[INFO] Topic '/race6/comm_test_rx' [...] receiving data from network
[INFO] Topic '/mbn/droneN_odom' [nav_msgs/Odometry] receiving data from network   ← 要 mavros 在跑
```

### 3.4 分项验证（脚本会自动打印表格）

`comm_ground_test.launch` 已经同时起了三个验证脚本，看它们的表格即可：

| 脚本 | 看什么 | 通过标准 |
|---|---|---|
| `race6_time_sync` | `offset` 均值/峰值、`rtt` | `\|offset\|` 峰值 **< 50 ms**，`rtt` 几毫秒 |
| `race6_comm_test` | 丢包率、内容损坏、单向延迟 | 丢包 **0%**、损坏 **0**、延迟 < 50 ms、无负延迟 |
| `race6_mintraj_test` | **`dt`**（= FSM 判据）、丢包、内容 | 丢包 **0%**、`\|dt\|` 峰值 **< 250 ms** |

**只有 `race6_mintraj_test` 的 `dt` 列才是真正的验收线** —— 它就是
`ego_replan_fsm.cpp:1223` 那个差值：`dt = 本机 ros::Time::now() − msg.start_time`。
在 PC 单机自测时它必然接近 0（同一个钟）；**真机上它才第一次变成"两个钟之差 + 网络延迟"，所以这一列比 PC 自测重要得多。**

### 3.5 里程计通道（真机独有，最直观的一项）

# 看对端的位置（从网络来的）

rostopic hz   /mbn/drone4_odom                             # 期望 ≈ 20 Hz

两边位置**基本一致**（静止时差几厘米以内）= 里程计真的跨机传过来了。

## 5. 阶段五：接上真正的 `ego_planner`（下一步）

通讯通了之后，把 planner 接上才是"飞机之间真的在传轨迹"。

```bash
# 每台：一个终端起通信
bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh <物理编号>
#      另一个终端起 planner（用你们实机那条 launch）
roslaunch ego_planner drone_inspect_new.launch drone_id:=<软件编号>
```

**怎么确认真的在传轨迹：**

```bash
rostopic hz /broadcast_traj_from_planner     # 本机发出的轨迹（重规划约 1~2 Hz）
rostopic hz /broadcast_traj_to_planner       # ★ 从网络收进来的别机轨迹（planner 真正消费的输入）
rostopic echo -n1 /broadcast_traj_to_planner | head -20    # drone_id 应是对端机号
```

### 5.1 ★ 不飞也能保障"真规划时通讯没问题"（三段式）

**核心认知：不要把"跑起来真规划"当作通讯验收的前提。** 通讯只负责搬运，
`/broadcast_traj_from_planner` 这条通道在**有没有 planner 时是同一个通道** ——
话题名、消息类型、Multibotnet 端口、序列化路径完全一样，区别只是"谁往话题里放消息"。

| 段 | 做什么 | 不依赖什么 | 能证明什么 |
|---|---|---|---|
| **A** | `roslaunch race6_comm comm_ground_test.launch …`（自带 `race6_mintraj_test`） | 不需要 mavros、不需要解锁、不需要 planner | **通道本身通了**：脚本自己造合法的 `MinTraj` 走真实通道，对端在 `/broadcast_traj_to_planner` 收到，并打出 `dt`（= FSM 判据）。**A 段 PASS ≈ 真规划时这条通道也通** |
| **B** | 起 mavros + planner，**发一次 trigger**，让 FSM 真的规划一轮 | ★ 桨叶卸下、**不起 px4ctrl**（没有东西执行 `/position_cmd`，飞机不会动） | **planner 真能把轨迹发出去**：`rostopic hz /broadcast_traj_from_planner` 有数、对端 `recv` 计数增长 |
| **C** | 对端观察 FSM 反应 | 同上 | **轨迹被真正消费**（不只是收到）：出现 `SWARM_CHECK` 状态切换或 `swarm distance … too close!` 告警，说明对端已把这条轨迹用于避碰计算 |

**A 段为什么够用**：`race6_mintraj_test` 造的是结构合法的 3 段 MINCO 轨迹（`order=5`、
`duration.size()==inner_x.size()+1`），并逐个字段比对内容完整性 ——
它压的就是 `RecvBroadcastMINCOTrajCallback` 的**全部解析与校验路径**。

**B 段怎么做（关键是把飞机"钉"在地上）**：

```bash
# ① 起 mavros（要 odom 才有数据；飞控上电、串口连好、桨叶卸下）
roslaunch mavros px4.launch
rostopic hz /mavros/local_position/odom            # 必须有数据，否则 planner 会一直卡 INIT
# ② 另开终端起 planner（★ 不要起 px4ctrl，飞机就不会动）
roslaunch ego_planner drone_inspect_new.launch drone_id:=<软件编号>
#    FSM 会打印 "state: INIT, Drone:N. Waiting for odom,target,trigger," —— 正常
# ③ 发一次 trigger，让 FSM 离开 INIT 去读航点并规划
rostopic pub -1 /traj_start_trigger geometry_msgs/PoseStamped \
  '{header: {frame_id: "world"}, pose: {pose: {position: {x: 0.0, y: 0.0, z: 1.0}, orientation: {w: 1.0}}}}'
# ④ 看它有没有真发出去
rostopic hz /broadcast_traj_from_planner           # 期望 1~2 Hz
rostopic echo -n1 /broadcast_traj_from_planner | head -5   # drone_id 应等于本机软件编号
```

**两条禁令**：

1. **`race6_mintraj_test` 不要在真 planner 运行时同时跑** —— 它造的假轨迹
   `drone_id` 就是本机编号，对端会当成"这台飞机的真实轨迹"参与避碰，把数据搅浑。
   A 段和 B 段**分开做**。
2. **没卸桨、或 px4ctrl 在跑时，不要发 trigger** —— FSM 一旦进入 `EXEC_TRAJ`
   就会向控制器发 setpoint，飞机会真的动。

### 5.2 FSM 卡住的常见状态与含义

| 打印 | 缺什么 | 处理 |
|---|---|---|
| `state: INIT, … Waiting for odom,` | **本机完全没收到 odom** | 起 mavros；或让 `odom_topic` 指向真正在发 odom 的话题（`rosnode info /ego_planner_node` 看它订阅了谁） |
| `state: INIT, … Waiting for odom,target,trigger,` | odom 没有；`target/trigger` 是**还没轮到设置**（`readGivenWpsAndPlan()` 在 `init()` 的等待循环之后才跑） | 先解决 odom，再发 trigger |
| `state: WAIT_TARGET, … Waiting for target,trigger,` | odom 好了，还差 trigger | 发一次 `/traj_start_trigger` |
| `state: SEQUENTIAL_START … Waiting for prev traj,` | **没收到 drone 0 的轨迹** | 查编号（六台软件编号必须有 0）或通讯链路 |
| 一直刷 `Replan` 但无 `Success=no` | 正常规划中 | — |

**三个必须注意的点：**

1. **起跑顺序 / 编号**：`ego_replan_fsm.cpp:185`（真机版；仓库快照版是 `:173`）要求
   `drone_id<=0` 或 `have_recv_pre_agent_`，后者靠"收到 drone 0 的轨迹"触发
   ⇒ **物理 1 号机（id 0）必须先广播起来**，否则其余各台永远停在 `SEQUENTIAL_START`。
2. **`advanced_param_swarm.xml:42` 有绝对路径** `/opt/datafs/config/swarm_param.yaml`，
   机上没有这个文件 roslaunch 会直接报错退出 —— 上机前确认它存在或改成包内相对路径。
3. **通讯不通，后面的飞机永远不起飞** —— 所以 A 段验收必须先过。

## 7. 附录 B：故障速查（按症状）

| 症状 | 最可能的原因 | 处理 |
|---|---|---|
| `rospack find race6_comm` 找不到 | 包没进 `chen_ws/src` / 这个终端没 source / rospack 缓存旧 | `WS=$HOME/chen_ws bash .../setup_six_ws.sh --minimal --no-lab` → `source ~/chen_ws/devel/setup.bash && rospack profile` |
| `RLException: ... is neither a launch file in package` | 同上 | 同上 |
| `Invalid roslaunch XML syntax: not well-formed` | **launch 注释里出现了连续两个减号 `--`** | 报错给了 `line X, column Y`，去那附近改掉；`grep -n -- '--' *.launch` |
| `Failed to load config` | YAML 少了必填键 | `send_topics` 必须有 `max_frequency`+`bind_address`；`recv_topics` 必须有 `connect_address` |
| **发送在涨、接收全是 0，且毫无报错** | **配置表 `<-` 后面显示成"名字"= 别名没定义**（`resolveAddress` 会原样返回字符串，ZMQ 当主机名，静默连不上） | 看配置表那几行；`check_config.py --all` 会直接指出 |
| `Multiple packages found with the same name` | 往 `chen_ws` 里塞了第二份实验室包 | 删掉多出来的那份，改用 `--no-lab` |
| `Failed to bind to ...:4001` | 同一台主机上起了两份同一配置（单机仿真要错开端口） | 真机多主机不会遇到；仿真请按机号错开端口 |
| 对端收不到 / 一台能一台不能 | 两个方向有一边配置写错（IP、别名） | `check_config.py --all` 查跨文件一致性 |
| `dt` 是个恒定大数 | **系统时钟没对齐** | `chronyc tracking`；先解决时钟，别去调网络 |
| `race6_comm_test` 报负延迟 | 同上 | 同上 |
| 丢包高 / rtt 大 | 无线质量 | 拉近距离、换信道；`compression` 关掉；`max_frequency` 降到 10 |
| 网络被打满 / CPU 100% | **发和收用了同一个话题名**（广播风暴） | 检查配置：四条通道的发/收名字必须两两不同 |
| `HP: requesting home position` 刷屏（mavros） | PX4 还没给 home（室内未解锁时正常）；Ctrl+C 停不掉是因为它用 `&` 起在后台 | `rosnode kill -a`，或 `pkill -INT -f roslaunch` |
| FSM 一直刷 `SEQUENTIAL_START ... Waiting for prev traj,` | ① 六台编号没有 0 ② 通讯没通 | 查编号表（阶段 0）与通讯验收（阶段三） |
