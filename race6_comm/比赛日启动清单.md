# 比赛日启动清单（六机真机）

> **每台飞机都按同样的顺序做。** 顺序不是习惯问题，是一条**有依赖的链**（下一节有理由）。
> 本文档区分两类内容：**【已核对】**= 我在真机代码里读过对应文件；**❓待确认**= 需要你对照实物确认。
> 配套：`测试全链路.md`（联调阶段）、`README.md`（通讯原理与排查）。

---

## 0. 顺序总览与理由

```
① 网络 + 时间同步   →  ② mavros   →  ③ 雷达/相机驱动   →  ④ 状态估计/建图（FAST_LIO / MLMapping）
                                                            ↓
        ⑦ px4ctrl（控制器）  ←  ⑥ 起飞 + 触发  ←  ⑤ planner  ←  ④b 通信（Multibotnet）
```

| # | 做什么 | 依赖理由（★ 顺序不能颠倒的原因） |
|---|---|---|
| ① | 确认 IP 互通 + **chrony 时间同步** | **必须在起任何 ROS 节点之前**。校时会步进/拨动系统时钟；ROS 已经跑起来再拨钟，正在执行的轨迹和计时器会错乱 |
| ② | `mavros` | 它提供 `/mavros/imu/data_raw`（雷达/建图要）、`/mavros/local_position/odom`（planner 和 px4ctrl 都要）。**没有它，planner 会永远卡在 `INIT`** |
| ③ | 雷达驱动 / 相机驱动（RealSense） | ④ 依赖原始数据（点云、深度图、IMU） |
| ④a | `FAST_LIO`（mid360 雷达惯导）和/或 `MLMapping`（L515+T265 深度+位姿） | **必须在 planner 之前**：planner 的点云和 odom 都从这里来；晚起就会出现"planner 卡 INIT / 地图是空的" |
| ④b | **Multibotnet**（通信） | **必须在 planner 之前**：planner 一启动就会开始规划并广播；通信没起来，第一次重规划就不带别机轨迹 → 多机避碰从第一帧就是瞎的 |
| ⑤ | `ego_planner`（planner） | 依赖 ②③④ 全部就绪；此时开始广播轨迹 |
| ⑥ | 起飞（px4ctrl 的 takeoff）+ 发 `/traj_start_trigger` | 触发要**在飞机稳定悬停之后**发（planner 用当前 odom 作为轨迹起点） |
| ⑦ | `px4ctrl`（控制器） | 它订阅 `/position_cmd`，把 planner 的指令变成姿态/推力。**没起它，planner 规划得再好飞机也不会动** |

> **两句话记住**：**"感知 → 通信 → 规划 → 控制"**；**"时钟和网络在一切之前"**。

## 1. 赛前准备（全部飞机，一次做完）

```bash
# ① 六台接同一个 AP（For_Drone_5G），建议配静态 IP（否则换电池后 IP 会变、配置失效）
hostname && ip -4 addr show | grep -w inet

# ② 两两 ping 通（6 台随便挑，重点确认 1 号机）
ping -c 3 192.168.66.161

# ③ 代码版本六台一致（输出必须相同）
git -C ~/SixBotsRace rev-parse --short HEAD

# ④ 配置自检（含六份配置的 IP 一致性）
python3 ~/SixBotsRace/race6_comm/scripts/check_config.py --all

# ⑤ 时间同步（★ 在起 ROS 之前）
#    物理 1 号机 = 源机：
sudo systemctl restart chrony && sudo systemctl enable chrony
chronyc tracking                       # 源机看 RMs offset 即可
#    其余各台 = 客户端（server 指 1 号机）：
systemctl is-enabled chrony            # 期望 enabled
chronyc sources -v                     # 期望源机那行前面是 ^*
chronyc tracking                       # ★ 客户端上 System time ≈ 两机时钟差
```

**时间同步三条件**（每台查一遍）：`systemctl is-enabled chrony` = enabled、`systemd-timesyncd` = disabled、**源机（物理 1 号机）在网**。

### ★ 1.1 源机（物理 1 号机）挂了 / 找不到源，会发生什么

**分三层看，结论是"缓慢退化，不是悬崖"：**

**① chrony 层：不会崩，只会"失去纪律"**
- 客户端写的是 `server 192.168.66.101 iburst`，chrony 会**无限重试**，源一回来就自动重连
- 源不可达时：`chronyc sources` 里那行从 `^*` 变成 `^?`；`chronyc tracking` 的 `Leap status` 变成 `Not synchronised`
- **系统时钟继续走**（内核按"最后学到的频率偏差 + drift 文件"自由运行）—— **不会停、不会跳回、不会清零**

**② 漂移速度：缓慢（这是关键，不用担心"一挂就废"）**
- `chronyc tracking` 里的 **`Skew`** 就是频率误差上界；机载 SBC 典型 **1~50 ppm**
- 20 ppm ≈ **1.2 ms/分钟 ≈ 72 ms/小时**；两台各自反向漂 → 相对差增长约 **2.4 ms/分钟**
- ⇒ **从 0 漂到 FSM 的 250 ms 告警线，大约 1.5~2 小时**（最差 50 ppm 时约 50 分钟）
- ⚠️ **前提**：失去源**之前**必须已经同步好。若源挂时本来就差了 100 ms，余量就只剩 150 ms

**③ FSM 层：两个独立后果，第二个更致命**
- **时钟差**：`|t_now − msg.start_time| > 0.25 s` 才刷 `Time stamp diff` 告警，`> 10 s` 才丢弃轨迹 ⇒ **几分钟内完全无感**
- **★ `drone_id = 0` 缺失**（物理 1 号机同时也是 0 号机）：
  - 它在起飞前就挂了、**从没广播过轨迹** → 其余五台的 `have_recv_pre_agent_` 永远为 false → **整个任务无法开始**
  - 它**广播过一次之后再挂** → 其余台的 `have_recv_pre_agent_` 已是 true，**可以继续飞**（只是不再避让它）

### 1.2 三层预案

| 层 | 做法 | 适用 |
|---|---|---|
| **① 最佳：把源从"飞机"挪到"地面站"** | 地面 PC 装 chrony 当源（`allow 192.168.66.0/24`，有外网再加 `pool ntp.aliyun.com iburst`）；各飞机改成 `server <PC的IP> iburst`。PC 不会摔、不靠电池、CPU 充裕，**还能让绝对时间也准** | **正式比赛推荐** |
| **② 次佳：客户端配「主 + 备」多源** | 客户端多写几行 `server`，并让备选那台也配 `local stratum 8` + `allow`。chrony 自动在可达的源里选，主挂了自动切 | 没有地面站时 |
| **③ 兜底：飞行中发现偏差在涨** | **绝不在空中校时**。继续飞（漂移缓慢），落地后重新同步；下一轮开始前必须重新对时 | 任何情况 |

**② 的具体配置**（每台**客户端**）：

```
driftfile /var/lib/chrony/chrony.drift
server 192.168.66.101 iburst prefer     # 物理 1 号机（主）
server 192.168.66.100 iburst            # 物理 2 号机（备）
server 192.168.66.161 iburst            # 物理 3 号机（备）
makestep 0.1 3
rtcsync
```

同时在**被当备选的那两台**上确认（否则它们无法被当源）：
```
allow 192.168.66.0/24
local stratum 8
```

⚠️ **bootstrap 注意**：六台同时冷启动、时钟各差几秒时，chrony 面对多个**同级**源可能报
`no majority` 而一个都不选。所以启动次序上仍然**先起物理 1 号机**（让它先成为唯一权威），其余台再起。

**监控命令**（起飞前必看 + 飞行中定期看）：

```bash
chronyc tracking | grep -E 'System time|RMS offset|Skew|Leap'   # 客户端：System time = 与源的当前偏差
chronyc sources -v | grep -E '\^\*|\^\?|\^\+'                   # ^* 在用 ｜ ^? 不可达 ｜ ^+ 备选可用
```
阈值建议：`System time` **> 50 ms 就停下来查**；**> 250 ms 不要起飞**。

### 1.3 0 号机缺失的预案（"源机挂了"里最容易被忽略、后果最重的一条）

`drone_id = 0` 是算法**硬要求**（`have_recv_pre_agent_` 只认 0 号机的轨迹），所以必须**提前准备**：

- 指定一台**备用机**，预先准备好它的 `config/race6/drone_0.yaml` 和启动脚本；物理 1 号机不能飞时用它顶 `drone_id:=0`
- 更彻底的做法：**把"时间源"和"0 号机"两个角色分开** —— 时间源用地面 PC（预案①），
  这样即使 0 号机在起飞前挂了，也只是"起跑逻辑"受影响，不会同时把时间同步也带走
- ⚠️ **绝不能两台同时用 `drone_id:=0`**：同 id 会在各机的 `swarm_traj` 里互相覆盖，避碰数据全乱

### ④b 通信 —— Multibotnet【已核对】

```bash
source ~/chen_ws/devel/setup.bash

# ★ 比赛日必须加 --race（只起 Multibotnet，不起任何测试脚本）
bash ~/SixBotsRace/race6_comm/scripts/race6_launch.sh <物理编号> --race

# 验证（★ 只看配置表 Receive Topics 那几行）
#   /broadcast_traj_to_planner <- 192.168.66.161:4001     ← 必须是【IP】，不是名字
#   并出现 "receiving data from network"
```

> **★ 为什么必须加 `--race`**：不加的话起的是 `comm_ground_test.launch`，它**自带三个测试脚本**，
> 其中 `race6_mintraj_test` 会往 `/broadcast_traj_from_planner` **发假轨迹**，
> 对端 FSM 会把它当成"这台飞机的真实轨迹"参与避碰计算 —— **比赛日带着它飞 = 数据被污染**。
>
> `--race` 走的是 `multibotnet_node.launch`（纯通信）。其余两条路等价：
> ```bash
> # 想同时保留时间同步监控（它不发任何 planner 会消费的东西，安全）：
> roslaunch race6_comm comm_ground_test.launch drone_id:=<软件编号> peers:=<对端> \
>     config:=/abs/path/drone_<id>.yaml run_comm_test:=false run_mintraj_test:=false
> # 或者完全手写（不用脚本）：
> roslaunch race6_comm multibotnet_node.launch drone_id:=<软件编号> \
>     config:=$(find race6_comm)/config/race6/drone_<软件编号>.yaml
> ```
>
> **`race6_launch.sh` 仍然值得用**，因为它顺手做了三件比赛日很需要的事：
> ① 物理编号 → 软件 `drone_id` 的换算（防"六台全不起飞"）
> ② `peers` 自动算对（六台全上时不带 `--pair`）
> ③ **★ 校验本机真实 IP 与配置里 `drone<id>` 那一行是否一致，不一致直接拒绝启动**
>    —— 这是现场最实用的一条防线（专治"配置拷错机器 / IP 没改对"）

## 3. 六机的启动次序（★ 有硬约束）

| 顺序 | 哪台 | 为什么 |
|---|---|---|
| **第 1 个** | **物理 1 号机**（软件 `drone_id = 0`） | ① 它是 **chrony 时间源**，其余各台要跟它对齐 ② `ego_replan_fsm.cpp:185` 的起跑条件是 `drone_id <= 0 \|\| (>=1 && have_recv_pre_agent_)`，而 `have_recv_pre_agent_` 只认 **`drone_id = 0` 的轨迹** ⇒ **0 号机不先广播，其余五台永远不会起飞** |
| 第 2~6 | 其余各台 | 依次起来，等自己那台稳定悬停后各自发 trigger |

**判定是否正常**：其余各台的 FSM 不能一直刷
`state: SEQUENTIAL_START, Drone:N. Waiting for prev traj,` —— 一直刷就是"没收到 0 号机的轨迹"。

## 5. 出问题时的回退顺序（停机）

**反着来**：控制 → 规划 → 通信 → 感知 → mavros。

```bash
# 单台快速停干净（在每台上）
rosnode kill -a 2>/dev/null
pkill -INT -f roslaunch 2>/dev/null; sleep 2
pkill -9 -f mavros laserMapping fastlio_mapping px4ctrl 2>/dev/null
ps -ef | grep -E 'roslaunch|rosmaster|mavros' | grep -v grep    # 应无输出
```

> **★ 飞行中不要做的事**：不要 `chronyc makestep` / `race6_time_sync.py --apply`（步进时钟会毁掉正在执行的轨迹）；
> 不要 `rosnode kill -a`（会瞬间失去控制）。
